1. THE PIPELINE AS IT ACTUALLY IS
──────────────────────────────────────────────────────────────────────────────
MT5 executes trades it receives as TELEGRAM ALERTS (telegramNotifier.ts — "the
downstream MT5 executor"). One emission projects into THREE legs with
DIFFERENT durability:

  Leg 1 ALERT       sendTelegramAlert → INSERT telegram_outbox_v1 (durable)
                    → Edge Function send-telegram-alert → api.telegram.org
                    → pg_cron drain retries every minute until DELIVERED or
                    AGED_OUT (10-min TTL). CRASH-PROOF: survives app death.
  Leg 2 SERVER ROW  signalEngine.ts:10088 pushEmittedSignalRecord →
                    emitted_signals_v1. Fire-and-forget. Dies with the process.
  Leg 3 LOCAL UI    TradingContext: alert fired FIRST (:2914), then
                    setSignalHistory → persistSignalHistory → AsyncStorage
                    'signal_history'. `void flushHistoryWrite()` — fire-and-
                    forget. Dies with the process.
  Leg 4 EXECUTION   Telegram → MT5 EA. NO ack, NO telemetry. Unobservable.

Recovery path that exists: Item 194 reconcileHistoryFromServer
(TradingContext:850-900, called at boot :2616, both branches) backfills local
history from emitted_signals_v1 (7-day window, newest-200) — but ONLY if Leg 2
landed. Nothing reconciles from Leg 1. Nothing observes Leg 4.

──────────────────────────────────────────────────────────────────────────────
3. VERDICT — DIRECTION A: "MT5 executed, app never showed it"
──────────────────────────────────────────────────────────────────────────────
ROOT CAUSE: the alert leg is the only crash-proof leg. Emission order is
  server-row (fire-and-forget) → alert (durable) → local history (fire-and-
  forget). If the app process dies/reloads between the alert landing in the
  outbox and the two record writes landing, the drain still DELIVERS the alert
  → MT5 executes — while BOTH records are gone. The 3 pasted cases prove this
  happened 3 times in 14 days. Because their emitted_signals_v1 row never
  landed, the Item 194 boot reconcile has NOTHING to backfill from → those
  signals are permanently invisible in the app. (They predate ITEM 225(B3):
  the witness message carried no CONFIDENCE, and emitted_signals_v1.confidence
  is NOT NULL — documented unrestorable. B3 added CONFIDENCE to the message so
  the NEXT such row is fully restorable.)

For emissions whose server row DID land (today's 4): the next app boot
backfills them into history automatically. "Not even in history" for those is
therefore a timing/viewing state: (a) the app has not completed a clean boot
since — the hosted preview reload-loop class (the superseded repair's last
open item: verify the next managed public sourceHash); or (b) the user is
looking at a DIFFERENT device/browser than the one that emitted (each has its
own AsyncStorage; the boot reconcile self-heals within 7 days).

──────────────────────────────────────────────────────────────────────────────
4. VERDICT — DIRECTION B: "app shows a signal, MT5 never executed it"
──────────────────────────────────────────────────────────────────────────────
In 14 days there are ZERO app-side gaps: every one of the 76 emissions got an
outbox row and ALL 79 rows are DELIVERED (Telegram accepted them). The old
silent-loss era (ITEM 6: Rork backend flapped 503, 2.4s retry, error
swallowed) is gone; historical pre-outbox signals still sitting in the app's
AsyncStorage history can legitimately have never alerted — but going forward,
any "in app, not on MT5" is DOWNSTREAM OF DELIVERY:
  - The alert carries ENTRY ZONE = entry ± $2.0; the derived aging measurement
    (measureAlertAgingHorizon) says only ~59.7% of alerts are still price-
    executable at +10m, ~76% at +5m. The outbox deliberately ages alerts at
    10 min rather than deliver stale ones.
  - The EA applies its own zone/staleness/session/position filters — the
    system has NO ack, so an EA skip is indistinguishable from silence.
So Direction B is an observability gap, not a delivery gap (post-outbox era).
